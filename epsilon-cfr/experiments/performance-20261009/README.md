# CFR collector / learner 性能比較

2026-10-09、RX 7900 XTX 24 GiBの物理GPU 0で実測。比較元は`44c07f4`です。既存の学習runを更新せず、同じcheckpoint・開始局面・seedを使って独立した出力先で測定しました。

## 結果

| 指標 | 変更前 | 採用版 | 倍率 |
| --- | ---: | ---: | ---: |
| CFR収集 decision/s | 13,285 | 24,147 | 1.82 |
| CFR learner 抽選数/s（通常の重み付き抽出） | 5,730 | 9,209 | 1.61 |
| 上記の重複集約後の実処理行/s | 631 | 1,014 | 1.61 |
| CFR learner 実処理行/s（重複なし診断） | 2,150 | 3,576 | 1.66 |

Nanoと同等の速度には達していません。Nanoの本番learnerは17,176 → 17,197行/s、収集は82,852 → 81,056推論要求/sでした。収集は単回の測定値で、対局内容とbatch構成にも揺らぎがあります。各経路の処理範囲の差は以下に記載します。

重み付き抽出の比較には、実効サンプル数3.88・最大抽選確率48.4%の同じreplayを使っています。131,072回の抽選に対し、更新内の重複をまとめた実処理は14,438行です。抽選数/sだけを示すと実際の計算能力を過大に見せるため、両方を掲載しています。

[設定と測定結果](results.json)、[数値比較](numerical-checks.json)、[CFR設定](cfr.toml)、[Nano設定](nano.toml)を保存しています。採用版の全モジュール通常テスト904件、CPU/nativeの対象検証53件、GPU検証19件が成功しました。変更Javaファイルはgoogle-java-formatで整形・確認しています。一時的な診断コードは本番へ含めていません。

## 測定範囲

- CFR収集: `HAND_GRP` 4,096局、warmup 256局。本人の観測履歴、全席の判断、ロン見逃し／九種九牌の分岐比較、CPUの固定GRP、Zstd圧縮、ファイルfsync、atomic公開、保存待ちを含みます。
- CFR learner: 同じ比較元の収集データから同じseedで抽出。global batch 1,024、microbatch 512、warmup 8更新。通常の重み付き抽出は128更新、重複なしの計算量診断は64更新。32更新ごとのcheckpoint保存とGPU完了待ちを含みます。
- `uniform-distinct`は保持行から重複なく抽出する診断です。本番LCFRの抽選分布ではなく、学習品質を評価する実験でもありません。学習設定には採用していません。
- Nano収集: 4,096半荘、warmup 256半荘。本番の収集経路です。全席の推論要求数と1席分の保存行数を区別します。
- Nano learner: 本番のActor/Value learner、各測定で同じ完了ゲーム集合を使うwarmup 1 pass、測定1 pass。比較元664,035行・採用版664,647行、32 optimizer steps、microbatch 4,800。入力展開・転送・順逆伝播・optimizer・KL検査・GPU完了待ちを含み、checkpoint書き出しは含みません。

1局と1半荘、推論要求と保存された判断、重み付き抽選回数と重複集約後の実処理行数は同じ指標ではありません。Nanoとの比較は各本番経路の処理能力の比較であり、同一の学習課題を実行した比較ではありません。

## 実装

- Nanoの共通feature spine、候補表現、状態fusion、転送・実行パイプラインをCFRから利用。凍結推論用の低精度パラメーターを独立所有し、保存モデルを変更しません。
- 入力生成、推論、エンジン進行を完了イベントで接続。同時応答の全入力が使い終わるまで、その盤面を変更しません。
- 完了したepisodeの圧縮保存を4ワーカーへ分担。保存待ちと保存中の合計を16件に制限し、全ファイルの保存成功後にだけ収集を完了します。
- learnerは同じ更新内の重複を出現回数へ集約し、近い履歴長をまとめてGRUを実行。候補bucketへ出力を振り分け、損失を合算して逆伝播します。

## 数値検証

FP32では損失・全パラメーターの勾配・複数回のAdamW更新を比較します。BF16はbatch形状が変わると丸めが変わるため、損失だけでなく勾配ベクトル、共通の初期重みからの累積更新量と方向、方策の確率・KL・最大確率の手の差を確認します。

履歴batch統合の3回反復診断では、変更前の処理を繰り返しただけでも累積更新ベクトルの相対差は最大0.575%でした。最適化版との差は最大2.509%、cosineは最小0.999685。完全なbit一致ではなく、batch構成変更によるBF16の丸め差を含みます。これを対戦強度の改善や長期学習の同一性の証明とは扱いません。

## 採用しなかった最適化

- learnerの盤面特徴を候補bucket間で共有: 処理速度は重み付きで3.57%、重複なしで4.50%改善しましたが、BF16の初期勾配ベクトル差が1.81%、cosine 0.999839となり、既存の基準（相対差1%以内・cosine 0.9999以上）を満たしませんでした。この追加変更は戻し、履歴GRUの共有だけを採用しました。
- microbatch 256 / 512 / 1,024: 履歴batch統合・非同期収集版で同じglobal batch・同じ抽出行・同じ更新数を使い、重複なしの処理速度はそれぞれ2,857 / 3,566 / 3,537行/秒でした。512を維持します。
- 同一episode内の履歴prefix共有: 実データでprefixを照合しました。重複のない抽出ではpaddingを含む履歴処理量の削減は2.63%で、候補計算の呼び出し数は増えました。複雑な学習graph共有の導入は見送りました。
- GRUの明示的なBF16化: FP32 masterを保持した微分可能な変換で、単体の順逆伝播は61.0 → 38.9 ms。学習全体では重み付き9,209 → 9,441抽選/s、重複なし3,576 → 4,030行/sでした。ただし、AVERAGEの3回更新後の累積更新ベクトル差が3.129%（同じ採用版の反復差0.576%）となり、既存の3%基準を超えました。精度設定と実際の学習計算を変えるこの案は採用しませんでした。以前は「GRUはFP32」と説明しましたが、FP32はmaster parameterの保持型です。[追加の原因調査](../bottleneck-20261009/README.md)では、BFLOAT16設定でGRUの出力tensorがFLOAT16になることを確認したため訂正します。内部kernelの演算精度までは未特定です。最初の重複なし測定は差し替えクラスの指定漏れがあったため除外し、ロード元を確認した再測定値を記載しています。

設定・教師・学習率・抽選分布・global batch・履歴の長さ・optimizer更新数を速度のために変えていません。履歴を切り捨てたり、古い重みで計算したhiddenを学習に使い回したりする実装もありません。
