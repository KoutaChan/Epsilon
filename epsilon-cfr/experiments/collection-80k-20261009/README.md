# CFR収集の80,000判断/sに向けた最適化

保存込みの最良測定は **77,964.6判断/s** です。変更前の2回合算62,682.9判断/sから24.38%改善しましたが、80,000判断/sには未達です。測定値・起動コマンド・JARの識別情報は[results.json](results.json)に保存しています。

## 測定条件

Ryzen 9 9950X3D、Radeon RX 7900 XTXのGPU 0、Java 21、ROCm 7.2.2を使用しました。同じ凍結モデル・GRP・seed・TOMLで256半荘をwarmupし、4,096実半荘を測定します。特徴生成、推論、対局進行、GRP、分岐、ext4への圧縮保存、writer終了待ちを含みます。モデル読み込み、warmup、収集後の復号診断は含みません。本番の1反復32,768半荘という設定は変更していません。

通常経路はすべて4,096半荘、48,982局、4,367,409判断で一致し、入力形状ごとの件数も一致しました。判断数にはGPUの順伝播を省略したforced 1,197件を含みます。追加枝は非同期の予約枠に依存するため、件数の差を別に記録しています。batch数は収集側の投入回数であり、GPUの順伝播回数ではありません。

## 通常測定の結果

JFRを有効にした診断用runは、この表へ含めていません。基準は既存2回の合算、各候補は1回の測定です。小差の有意性や、32,768半荘の長時間性能は検証していません。

| 候補 | 主な変更 | GC | 判断/s |
| --- | --- | --- | ---: |
| 基準 `c114311` | 変更前、2回合算 | G1 | 62,682.9 |
| v1 | Nanoのcompact推論転送、保存配列への直接書き込み、入力計画の非同期化 | G1 | 68,692.6 |
| v1b | 入力長の定数時間計算、Zstdバッファ再利用 | G1 | 69,252.3 |
| v2 | 保存payload生成とGPU演算の並行実行 | G1 | 70,304.0 |
| v2b | 一行動一遷移の連続コピー | G1 | 70,101.6 |
| v3 | 上限付きの入力配列再利用 | G1 | 69,033.7 |
| v4 | 未完了batchがない時だけ次を供給 | G1 | 56,874.0 |
| v5 | Nanoの結合済み重みの再利用、盤面ごとの状態射影 | G1 | 70,273.2 |
| v3 | 同じv3 JARでGCだけ変更 | Generational ZGC | 77,162.7 |
| v5 | 同じv5 JARでGCだけ変更 | Generational ZGC | **77,964.6** |

v4は速度が悪化したため採用していません。供給制御はNanoと共通の方式を維持します。v2bとv3は単独の速度向上を確認できていません。v3の配列再利用は、別runのJFRによる割り当て量の推定値を171.1GBから112.7GBへ減らしました。ただしGC停止時間の減少は6.688秒から6.231秒に留まりました。

v5と同じJARでGenerational ZGCへ変えると、保存込み速度が10.94%改善しました。ZGCのGC停止合計は全プロセスで1.606msです。G1のJFR値は測定区間のみ、ZGCログは準備・warmup・復号診断を含むため、計測範囲を同一として扱いません。ZGCのRSSは複数mappingの影響があるので、RSSの大小からヒープの省メモリ効果は主張しません。

## 実装と検証

入力生成・推論用転送・重みを固定した候補表現にはNanoの実装を使います。CFRは確定済み入力から保存payloadを直接作り、GPU演算と並行して進めます。入力配列はGPUと保存処理の双方が読み終えてから再利用し、失敗・cancel・終了処理でも同じ所有権を保ちます。待機中の再利用配列は256MiBを上限にします。

v5は通常640件、native CPU178件、ROCm21件が成功し、全8モジュールのコンパイルも成功しました。ROCmではREGRET・AVERAGE、BF16・FP16、入力の再利用、非同期処理の完了待ちを確認しています。学習経路、パラメーター名、後悔教師・平均方策教師の計算、replayの抽出分布は変更していません。

次のv6では、遷移特徴の生成と状態加算・SiLUをNano既存の融合演算へ統合しています。融合の入口は2次元のviewに揃え、通常演算へのfallbackを避けます。CPU・学習・型が一致しない場合は従来の計算を使います。最終ソースで通常640件、native CPU181件、ROCm28件が成功し、全8モジュールのコンパイルとフォーマッタ検査も成功しました。失敗・skipはありません。保存込み速度の追加比較は未実施です。

追加比較はサーバーの容量確保待ちです。許可済みの古いpretrain生成キャッシュ7.58GBは整理しましたが、測定用データの削除は別途確認が必要となったため保持しています。最新候補の速度をv5の値で代用しません。

## 再現

Java 21でのGenerational ZGCの起動オプションは、`-XX:+UseZGC -XX:+ZGenerational`です。測定時はさらに`-Xms1g -Xmx20g -XX:MaxDirectMemorySize=6g`を指定しました。モデル設定だけではJVMのGC方式は変わりません。学習の起動例は[README](../../README.md#自己対戦で学習する)を参照してください。

測定にはテスト側の`CfrPerformanceBenchmark collect`を使います。クラスパス、モデル・GRP・TOML・出力先、環境変数は`results.json`の各runへ記録しています。元データはローカル`epsilon-cfr/target/cfr-80k-20261009`、サーバー`/home/koutachan/epsilon-ai/benchmarks/cfr-80k-20261009`へ保持しています。サーバーで学習中のrunは再起動していません。
