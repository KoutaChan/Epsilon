# CFRのmicrobatch上限比較

盤面入力版CFRで、global batchを1,024に固定し、microbatch上限512と1,024を比較しました。新規モデルの既定上限に1,024を採用します。収集数、抽選分布、更新数、学習率は変更していません。

## 速度

RX 7900 XTXのGPU 0で各条件を2回完走しました。2巡目は上限の実行順を逆転しています。数値は処理行数の合計を計測時間の合計で割った値です。[全測定値・設定・数値比較](results.json)を保存しています。

| 学習 | 上限512 | 上限1,024 | 変化 |
| --- | ---: | ---: | ---: |
| REGRET・重複なしの診断 | 9,478 行/s | 9,925 行/s | +4.7% |
| REGRET・通常の重み付き抽選 | 3,401 行/s | 3,425 行/s | +0.7% |
| AVERAGE・通常の重み付き抽選 | 9,758 行/s | 10,447 行/s | +7.1% |

いずれも重複集約後に実際に計算した行数です。通常REGRETの抽選速度は30,872→31,091抽選/sですが、これを実処理行/sやNanoの行/sと比較しません。通常REGRETは全128更新でbucketの最大が123行、計算分割数は双方256回と一致しました。上限変更は計算形状へ作用しておらず、0.7%差を最適化効果とは判断しません。

AVERAGEは全128更新で512行を超えるbucketがあり、最大643行でした。計算分割は404→276回へ減りました。重複なしの診断は本番と抽選分布が異なるため、計算性能の診断として扱います。

## メモリと比較条件

GPU 0全体の使用VRAMを20ms間隔で測定しました。モデル読込・warmup・測定窓を含むプロセス全体のピークで、フレームワークのallocated/reserved値ではありません。

| 学習 | 上限512・2回の範囲 | 上限1,024・2回の範囲 |
| --- | ---: | ---: |
| REGRET・重複なしの診断 | 3.16〜3.54 GiB | 5.24 GiB |
| AVERAGE・通常抽選 | 2.93〜3.27 GiB | 4.50 GiB |

通常REGRETは分割が同一にもかかわらずプロセス全体のVRAMピークが変動したため、上限変更によるメモリ改善とは解釈しません。途中に確認したROCmプロセス一覧では、測定用Java以外のGPU計算プロセスはありませんでした。複数GPUの速度は今回測定していません。

- 実装基準は`4b2e97e`。双方とも同じNano表現・ゼロ出力重み・初期AdamW状態から開始しました。AVERAGEはこの同じ初期パラメーターをAVERAGEの目的で学習する独立した測定用モデルです。
- 保存済みの同一4,096エピソード・362,527判断からreplayを作成。上限ごとに元checkpointを独立して複製し、重みとoptimizerの一致を確認しました。元データ、既存run、学習済みモデルは変更していません。
- BF16、hidden 256、学習率`2e-4`、global batch 1,024、同じ抽選seedを使用。warmupは8更新、計測は重複なし64更新、通常抽選128更新です。
- 同じ役割の比較間では抽選数、実処理行数、bucket内訳、replay重み、更新数、保存回数が一致しています。
- 速度は抽選・復号・転送・順逆伝播・optimizer・32更新ごとの保存とGPU完了待ちを含みます。コーパス準備、モデル読込、warmupは除外しています。

## 数値比較

同じパラメーター・AdamW状態から毎回比較する単更新の検証では、REGRET/AVERAGE×通常抽選/重複なしの各6更新、計24組が既存BF16基準を通過しました。数学的な損失の分母と勾配集約後の1回のclip・AdamW更新は同じです。

一方、初期状態から各モデルを独立して6回更新する追加診断では、累積更新ベクトルの差が3%基準を超えました。この失敗は記録を残しています。同じ上限512同士の対照実験も失敗し、最終差は次の値でした。

| 比較 | REGRET・重複なし | AVERAGE・通常抽選 |
| --- | ---: | ---: |
| 512対1,024・累積更新の相対L2差 | 4.422% | 3.798% |
| 512対512・同じ上限の対照実験 | 4.536% | 5.250% |

同じ上限でもBF16の独立した学習軌跡はこの厳密な累積基準を満たせず、今回の結果から上限変更に固有の異常とは判断できません。単更新の一致と実測の速度改善を根拠に採用しますが、長期の対局性能の同等性や、1,024のほうが数値的に安定することを示した結果ではありません。

## 適用

同梱TOMLと共通設定アノテーションのmicrobatch既定値を1,024に揃えました。実際の分割上限は`min(microBatchSize, ceil(抽選数 / デバイス数))`です。global 1,024なら1 GPUで1,024、2 GPUで512となり、上限引き上げで主要bucketが1台へ偏るのを抑えます。重複集約後の小さな行数から上限を計算し直すことはありません。

設定テスト10件と配布JARのビルドが通過し、変更したJavaをgoogle-java-format 1.28.0で整形しました。複数GPUの分割はコード上で確認していますが、その速度や数値差は今回実測していません。

既定値の引き上げは新規モデルへ適用されます。既存TOMLの明示値、既存runの保存設定、checkpoint内部のmicrobatch値は自動変更しません。デバイス数による分割上限の調整は既存モデルの実行にも適用されます。例えばglobal 1,024・保存済みmicro 512なら、2 GPUでは従来の512を維持し、4 GPUでは256へ分割します。この測定時点の収集予算は1反復32,768エピソードで、既定の`HAND_GRP`では32,768局でした。後続の半荘収集対応とは収集単位が異なります。global batchの1,024は1回の更新で抽選する判断数であり、収集する局数とは別です。
