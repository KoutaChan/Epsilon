# CFRの半荘収集と入力バッチ最適化

半荘収集へ変更済みの基準版に対し、容量区分ごとの入力を直接構築する最適化で、保存込みの収集速度が **54,816 → 62,921判断/s（+14.8%）** になりました。GPU 0で4,096半荘を各2回完走した値です。全測定値・実行条件・再現用ソースは[results.json](results.json)に保存しています。

## 収集の仕様と比較対象

既定の1 iterationは **32,768実半荘** です。`HAND_GRP`でも半荘を最後まで進め、各局を独立したLCFR軌跡として扱います。局末は固定GRP、半荘終端は実順位の効用を使い、重要度比を局内で計算します。反復の重み正規化に使うNは、32,768という半荘数ではなく、その反復で実際に保存した局軌跡の総数です。

この半荘化は収集分布の仕様変更です。後続局の開始局面は現在の方策が到達した分布となり、以前の局開始局面の生成方法と同じ学習分布にはなりません。今回の速度比較では両版とも半荘化済みで、同じモデルとGRPを読み込みます。32,768半荘の本番iteration全体や、この仕様変更による長期の強度は未検証です。

基準jarのSHA-256は`031be9f29fdfdae5386f20e42ffea0982250899a56912d289f79bb7de685aaf8`、最適化jarは`8d1529df11e85b84c3aaca2cf6a26deafe4c94affc8975a05ca801a402e58b9b`です。基準版にも半荘化とmicrobatch既定値の変更が入っています。基準版の`CfrModel`・`CfrInferenceWorkspace`・`CfrObservationCodec`だけが`4b2e97e`時点の構築経路であり、14.8%を同commitからの変更全体の効果とは解釈しません。

## 採用した実装

Nano共通の`DecisionBatchBuilder`で、同じ容量区分の観測を初めから一つの入力バッチへ書き込みます。従来の「一行ずつ構築し、推論直前に別のバッチへ複製して結合する」段階を除きました。各microbatchは元バッチの行ビューを転送し、保存payloadもその行から直接作ります。元の入力順、合法手、保存バイト列、forced判断の保持、不変payloadの所有権を維持します。

半荘の保存は局ごとに圧縮して追記し、完了した半荘について一度だけfsyncとatomic公開を行います。writerは4本・待機上限16で、同じ半荘の局を順序どおり処理します。これは両比較版に共通する保存経路です。

## 保存込みの収集速度

各プロセスで256半荘をwarmupし、その後の4,096半荘を測りました。GPU 0のみ、GRPはCPU、BF16、同時4,096半荘、最大推論4,096行、実行枠2、advance worker 32です。ロン見逃し・九種九牌の分岐を有効にし、半荘ごと上限1、同時上限8、追加推論比率上限0.01を使いました。

| 条件 | 測定秒（2回） | 判断/s（2回の合算） | 半荘/s（2回の合算） |
| --- | ---: | ---: | ---: |
| 半荘化済み基準版 | 79.4643 / 79.8830 | 54,816.23 | 51.4097 |
| 入力バッチ最適化版 | 69.2782 / 69.5441 | 62,920.84 | 59.0107 |

合算速度は処理件数の合計を測定時間の合計で割っています。各runの主経路は4,096半荘・48,982局・4,367,409判断で一致し、容量区分別の行数も一致しました。判断数にはforced 1,197件を含みます。forcedではネットワークの順伝播を省くため、見出しの判断/sをGPU順伝播行/sとは扱いません。

計測時間は特徴量生成、推論、エンジン進行、GRP、分岐処理、圧縮保存、writerの終了待ちを含みます。モデル読込、warmup、終了後の保存観測の復号診断は除外します。最終writer待ちは約5〜7msですが、保存は収集中にも並行して動くため、保存全体の費用がこの時間だけという意味ではありません。

分岐推論は基準版2,668 / 2,668行、最適化版2,584 / 2,582行でした。同じ設定でも非同期処理の進行によって分岐の成立件数が少し異なり、分岐まで含めた全仕事量の完全一致は主張しません。測定は同じseedの2回であり、複数seedの統計評価ではありません。

収集用checkpointの保存済み`modelConfig.microBatchSize`は512のままです。読み込んだモデルの設定をそのまま使った値であり、推論上限4,096とは別です。本番の新規学習モデルの既定microbatch上限1,024やglobal batch 1,024の比較は[別実験](../microbatch-20261009/README.md)を参照してください。

## Nanoとの参考比較

Nanoも同じGPU 0で256半荘warmup後、4,096半荘を2回収集し、payload保存・fragment公開・終了待ちまで計測しました。全評価席と分岐を含む推論要求は2,567,531 / 2,567,505件、速度は **80,349.75要求/s**、半荘速度は128.1832半荘/sでした。CFRの見出し速度との単純な比は約78.3%ですが、同一仕事量の性能比ではありません。

- CFRは4席の4,367,409判断を保持します。Nanoは半荘ごとに回す学習席1席の662,681 / 663,072判断を保持します。推論要求数と保存した教師行数は別の計数です。
- Nanoの学習済み方策とCFRの方策・探索が異なり、半荘の局数や判断数も異なります。同じseed番号でも系列間の山や軌跡は一致しません。
- Nanoのactor席はpolicyとvalue、相手席はpolicyのみを評価し、相手席のforced判断は推論要求に入りません。CFRの判断数には主経路のforcedを含み、分岐推論は別計数です。
- 同じ固定GRPを使い、分岐設定も揃えましたが、分岐の機会と終了条件まで同一ではありません。
- Nanoも本番の保存経路を使って終了まで待ちますが、その経路にはfsyncがありません。CFRの半荘公開にはfsyncを含みます。

この結果だけでNanoと同等の収集性能や学習速度を達成したとは判断しません。learnerの比較・不採用候補・保存時間の診断は[learner最適化実験](../learner-refinement-20261009/README.md)に分けています。

## JFRによる原因確認

通常の速度測定とは別に、両版を同じJFR設定で各1回記録しました。4本のwriterの開始から終了までを測定窓とし、対応するreportとの時間差は基準版0.165ms、最適化版0.114msです。warmupと収集後の復号を除外しています。記録時の収集時間は81.0622 → 69.2423秒で、この値を通常2runの合算へ混ぜていません。

| 測定窓内のJFR指標 | 基準版 | 最適化版 |
| --- | ---: | ---: |
| 推定Javaヒープ割当量 | 285.54 GB | 184.18 GB（−35.5%） |
| host stagingに分類された推定割当量 | 98.57 GB | 0.033 GB |
| GC停止回数 | 182 | 121 |
| GC停止時間合計 | 8.843秒 | 7.082秒 |
| 最大GC停止 | 321ms | 131ms |

`stage → concatenate → HostInputs`の重複入力生成に由来する割当サンプルは約97.15 GBから0になりました。Java実行サンプルの構成比は、特徴量生成52.5%→38.9%、保存用シリアライズ14.0%→32.5%、host staging 11.9%→8.5%です。最適化後にも不変payloadの保持用配列など、必要な保存処理は残っています。

GBは10進表記です。割当量は`ObjectAllocationSample.weight`による推定で、保持中ヒープ・RSS・VRAMや正確なbyte数ではありません。Java/nativeのサンプル構成比はCPU秒やGPUカーネル時間ではなく、構成比の増加だけで処理自体の悪化とは判断しません。GC停止は最上位の`GCPhasePause`を測定窓へ切り詰めて集計し、並行GCを含む`GarbageCollection`のdurationとは区別しています。profileの分岐推論も2,670 → 2,581行と少し異なります。

別途採取したVRAMはGPU 0全体、RSSはJavaプロセス全体を50ms間隔で観測した値で、準備・warmup・復号診断も含みます。開始時のGPU使用量にも差があり、allocator指標や今回の割当量削減と同一視しません。

## 検証と再現記録

通常647件、追加CPU native 21件、ROCm 8件が成功し、変更Java 37ファイルへGoogle Java Formatを適用しました。payloadのbyte一致、入力順序、並列エンコードの所有権、forcedと複数容量区分、複数microbatch、非一様な学習済み方策の推論一致を検証しています。長期の対局強度は未検証で、本番学習runの停止・再開は行っていません。

[results.json](results.json)には、全raw report・resource計測・終了コード、JFR比較と両版summary、再現helper・設定・コマンド、検証ログを収容しました。`evidenceFiles`の`content`を指定encodingで保存すると元のbyte列を復元できます。各項目に元サイズとSHA-256を付けています。JAR・JFR本体は埋め込まず、`provenance`に保存場所とhashを記録しました。追加した診断helperはGit管理外のtarget内に留め、本番コードへ計測出力を加えていません。
